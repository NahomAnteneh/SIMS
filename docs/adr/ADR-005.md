# ADR-005: No Redis in v1

## Status
Proposed

## Context
Redis is frequently introduced into distributed systems for query caching, session storage, and rate limiting. However, adding Redis introduces an additional distributed state store that requires high availability clustering (Sentinel or Redis Cluster), connection pool management, memory eviction tuning, and cache invalidation logic.

In an inventory system where state updates arrive continuously from multiple vCenters via PropertyCollector and EventHistoryCollector streams, maintaining cache coherence in an external cache is notoriously error-prone ("there are only two hard things in Computer Science: cache invalidation and naming things").

## Decision
Do NOT introduce Redis into the architecture for v1.
- PostgreSQL buffer pool (`shared_buffers`) will handle in-memory data caching natively.
- Query API responses will rely on optimized SQL queries, indexes, and HTTP cache headers (`ETag`, `Cache-Control`) where appropriate.
- Rate limiting and API token validation will be handled stateless-in-memory within the Query API instances or via PostgreSQL unlogged tables.

## Consequences
### Positive
- One less stateful infrastructure component to deploy, monitor, secure, patch, and back up.
- Zero cache invalidation bugs; search results are always strictly consistent with database state.
- Simpler local development environment and lower CI execution footprint.

### Negative / Trade-offs
- High query concurrency on identical search queries will hit PostgreSQL rather than an external key-value cache.
- Requires robust query indexing and execution plan caching within PostgreSQL.

## Alternatives Considered
- **Redis Cache-Aside:** Invalidate or update Redis keys on every vSphere event. Rejected due to extreme race condition complexity during event bursts.
- **In-Memory Go Cache (e.g., Ristretto/ccache):** Local to each API replica. Viable for static reference data (e.g., datacenter names), but dangerous for volatile inventory data.
