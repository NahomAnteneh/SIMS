# ADR-012: Topology Normalization and Hierarchy Representation

## Status
Proposed

## Context
vSphere inventory is intrinsically hierarchical and relational:
`vCenter` → `Datacenter` → `Cluster / ComputeResource` → `HostSystem` → `VirtualMachine`
Furthermore, VMs associate with multiple shared resources:
- Storage: Datastores (NFS, VMFS, vSAN)
- Networking: Distributed Virtual Switches (DVS), Standard Switches (VSS), Distributed Port Groups, VLANs
- Organization: Hierarchical Inventory Folders

A naive design might store entire VM hierarchies as denormalized JSON documents (`jsonb`). However, querying queries like "find all VMs connected to VLAN 100 on Cluster X" becomes prohibitively slow and expensive when unnesting large JSON blobs across hundreds of thousands of records.

## Decision
Adopt a normalized relational topology model with specialized PostgreSQL extensions:
1. **Normalized Entities:**
   - Dedicated relational tables: `datacenters`, `clusters`, `hosts`, `datastores`, `networks`, `distributed_switches`.
   - Foreign keys linking `virtual_machines` to `host_id`, `cluster_id`, and join tables for `vm_datastores` and `vm_networks`.
2. **Folder Hierarchy with `ltree`:**
   - Represent nested folder paths (e.g. `Datacenter1.vm.Engineering.Production`) using PostgreSQL's native `ltree` extension.
   - Enables high-speed subtree queries (e.g. `folder_path <@ 'Datacenter1.vm.Engineering'`) using GiST indexes.
3. **VLAN Representation with `int4multirange`:**
   - Represent complex VLAN trunk allocations (e.g. `10, 20-30, 100`) as PostgreSQL `int4multirange` types with GiST indexing.

## Consequences
### Positive
- High-performance relational joins and aggregations across topology boundaries.
- Native `ltree` support allows instant tree hierarchy queries without recursive Common Table Expressions (CTEs).
- Strict referential integrity prevents orphaned resources.

### Negative / Trade-offs
- Collector hydration logic must parse and normalize the complex vSphere SOAP hierarchy into relational rows.
- Schema migrations require structured DDL changes across multiple relational tables.

## Alternatives Considered
- **Pure Document/JSONB Model:** Easy to ingest raw SOAP outputs, but severely impairs search performance, filter indexing, and relational reporting.
- **Recursive Adjacency List (`parent_id` foreign key):** Slow recursive CTEs for deep folder trees; significantly outperformed by `ltree`.

## Proposed Amendment (Sprint 2): Streaming Topology Updates and Atomic Cache Swap
1. **Hybrid Propagation:** Topology changes stream in real time via the primary PropertyCollector filter (`name`, `parent`), and are persisted immediately to the normalized tables.
2. **Snapshot Mutability & Safety:** Changes mutate the active snapshot or trigger a new snapshot generation that is swapped atomically via `TopologyCache.Swap()`. A scheduled full sweep (default 15 minutes) ensures long-term consistency.
