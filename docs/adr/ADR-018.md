# ADR-018: vSphere Version Support Policy and Capability Flags

## Status
Proposed Amendment

## Context
Earlier revisions of the sprint plan (SPRINTPLAN.md Section 2.1) stated support for "vCenter Server 7.0.x through 8.x" and treated 8.x as a ceiling. That policy is outdated and architecturally restrictive:
1. **Upstream Release Status:** VMware vSphere 9.0 has been Generally Available since June 17, 2025 (initial build 24755229). The current 9.x line includes vSphere 9.1 (released May 12, 2026) and vCenter Server 9.1.1 (released September 2026).
2. **Upstream API Reference:** Broadcom's official vSphere Web Services API reference explicitly documents releases 9.1.1, 9.1, 9.0, 8.0U3, 8.0U2, 8.0U1, 8.0, 7.0U3, and 7.0 ([Broadcom Developer Portal](https://developer.broadcom.com/xapis/vsphere-web-services-api/latest/)).
3. **Client Library Capability:** Our pinned client dependency `github.com/vmware/govmomi` v0.56.0 states compatibility with "vSphere 7.0 and higher" ([README](https://github.com/vmware/govmomi#compatibility)). Furthermore, govmomi v0.56.0 generates its bindings from vSphere 9.1.0.0 (`vim25.Version = "9.1.0.0"` in `vim25/client.go`). The client library imposes no 8.x ceiling.
4. **Operational Failure Mode:** A hardcoded version ceiling prevents enterprise customers running vSphere 9.x from adopting SIMS and creates artificial service degradation during vCenter upgrades.

## Decision
1. **Open-Ended Support Policy (No Version Ceiling):**
   - The platform supports VMware vCenter Server **7.0 and higher** (7.x, 8.x, 9.x, and future releases) with **no hard-coded ceiling check**.
   - **Rejection (`unsupported_version`):** Any target reporting a detected product version strictly below 7.0 (e.g. 6.5, 6.7) is rejected at registration and connection with typed error `unsupported_version`.
   - **Acceptance:** Any target reporting a detected version $\ge 7.0$ is accepted.
   - **Compatibility Status:**
     - `compatibility = certified`: Assigned only when that major.minor (and patch level) has a real-vCenter verification column in `docs/vsphere-capability-matrix.md`.
     - `compatibility = untested`: Assigned with a warning when the version is $\ge 7.0$ but lacks an empirical real-vCenter verification column in the capability matrix.
     - A 9.x vCenter must **never** be rejected, and must not be reported as `untested` once its matrix column is empirically verified.

2. **Connect-Time Version & Identity Detection:**
   - At connection initialization, the collector queries `ServiceInstance.content.about` (`ServiceContent.About`) to read:
     - `Version` (e.g., `8.0.3`, `9.1.0`)
     - `ApiVersion` (e.g., `8.0.3.0`, `9.1.0.0`)
     - `Build` (e.g., `24022515`)
     - `ApiType` (`VirtualCenter`)
     - `ProductLineId` (`vpx`)
     - `FullName` and `InstanceUuid`
   - The session layer extracts `major.minor` (low cardinality) for structured logging, metric labels (`sims_vcenter_info{vcenter_id, major_minor, api_version, compatibility}`), and internal `collector_state`.
   - Version details and compatibility status are stored on the `vcenters` table and exposed over the management API (`POST /v1/vcenters`, `POST /v1/vcenters/test-connection`, `GET /v1/vcenters`).

3. **Capability Flags Over Version Branching:**
   - Behavioral differences between vSphere versions (and between simulator vs real appliance) must be driven by capability flags detected or negotiated dynamically, never by scattered `if version >= 8.0` branches:
     - **Tagging REST Endpoint Style:** In govmomi v0.56.0, `vapi/tags.Manager` issues requests using `/rest/com/vmware/cis/tagging/*`. While `/rest` was deprecated in vSphere 7.0U2 in favor of `/api`, it is retained for multi-version backward compatibility. The tag fetcher must be capability-driven with fallback, and must degrade gracefully via `ErrTaggingUnavailable` on failure without failing the core inventory pipeline (ADR-016).
     - **PropertyCollector Fault Handling:** Incremental change tracking uses `WaitForUpdatesEx`. The collector resilience layer handles both explicit `InvalidCollectorVersion` SOAP faults and transport timeouts (to handle vcsim's non-standard wait-loop behavior on stale tokens).
     - **Custom Attributes & Events:** Support both SOAP `CustomFieldsManager` (field definitions and VM `customValue`) and modern event structures across 7.x, 8.x, and 9.x.
   - A failed or missing capability degrades only that specific feature, never terminating the collector process or failing the entire vCenter connection.

4. **Client Library Negotiation:**
   - Govmomi `vim25.NewClient` initializes with `Version = "9.1.0.0"`. Upstream vCenter SOAP services handle forward and backward API negotiation natively. The client does not pin an obsolete version that modern 9.x vCenters reject. If needed, `soap.Client.UseServiceVersion()` can retrieve `/sdk/vimServiceVersions.xml`.

5. **Test Matrix & Multi-Major Fleets:**
   - **`vcsim`:** Executed on every pull request. Tests version parsing with mock `ServiceContent.About` fixtures for 7.0, 8.0, 9.0, 9.1, pre-7.0 (rejected), and future 10.0 (accepted, untested).
   - **Real vCenter Targets:** 7.0.x, 8.0.x (U3), 9.0.x, 9.1.x run nightly and pre-release (using available lab environments, recording which).
   - **Mixed Fleet:** Sprint 4 scale testing and cross-vCenter migration (xvMotion) validate concurrent operation across a fleet containing all available major versions.

## Consequences
### Positive
- Full compatibility with modern vSphere 9.0 and 9.1 deployments without code changes or ceiling blocks.
- Deterministic behavior: obsolete pre-7.0 endpoints fail fast with clear typed errors.
- Clean architectural decoupling: capability flags isolate version quirks from core hydration and streaming logic.
- Transparent operational status: operators can immediately see whether an environment is `certified` or `untested`.

### Negative / Trade-offs
- Certification requires maintaining and validating real vCenter testbeds across multiple major release lines (7.x, 8.x, 9.x).
- Managing fallback pathways between legacy `/rest` and newer `/api` REST endpoints increases test surface area.
