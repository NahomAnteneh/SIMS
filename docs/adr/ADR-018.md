# ADR-018: vSphere Version Support Policy and Capability Flags

## Status
Approved

## Context
Earlier revisions of the sprint plan stated support for "vCenter Server 7.0.x through 8.x" and treated 8.x as a ceiling. That policy is outdated and architecturally restrictive:
1. **Upstream Release Status:** VMware vSphere 9.0 has been Generally Available since June 17, 2025 (initial build 24755229). The 9.x line includes vSphere 9.1 (released May 12, 2026) and vCenter Server 9.1.1 (released September 2026).
2. **Upstream API Reference:** Broadcom's official vSphere Web Services API reference explicitly documents releases including 9.1.1, 9.1, 9.0, 8.0U3, 8.0U2, 8.0U1, 8.0, 7.0U3, and 7.0 ([Broadcom Developer Portal](https://developer.broadcom.com/xapis/vsphere-web-services-api/latest/)).
3. **Client Library Capability:** Our pinned client dependency `github.com/vmware/govmomi` v0.56.0 states compatibility with "vSphere 7.0 and higher." ([README](https://github.com/vmware/govmomi#compatibility)). Furthermore, govmomi v0.56.0 generates its bindings from vSphere 9.1.0.0 (`vim25.Version = "9.1.0.0"` in `vim25/client.go`). The client library imposes no upper version ceiling.
4. **Operational Failure Mode:** A hardcoded version ceiling prevents enterprise customers running modern vSphere environments from adopting SIMS and creates artificial service degradation during vCenter upgrades.

## Decision
1. **Open-Ended Support Policy (No Version Ceiling):**
   - The platform policy is worded consistently everywhere: **"vCenter Server 7.0 and above."**
   - **Rejection (`unsupported_version`):** Any target reporting a detected product version strictly below 7.0 (e.g. 6.5, 6.7) is rejected at registration and connection with typed error `unsupported_version`.
   - **Acceptance:** Any target reporting a detected version 7.0 or newer is accepted.
   - **No Upper Ceiling / No Untested State:** There is no named upper version, no per-major version lists, and no "untested" rejection or degradation state. Empirical validation is recorded per version in `docs/vsphere-capability-matrix.md`.

2. **Connect-Time Version & Identity Detection:**
   - At connection initialization, the collector queries `ServiceInstance.content.about` (`ServiceContent.About`) to read:
     - `Version` (e.g., `"8.0.3"`, `"9.1.0"`)
     - `ApiVersion` (e.g., `"8.0.3.0"`, `"9.1.0.0"`)
     - `Build` (e.g., `"24022515"`)
     - `ApiType` (`VirtualCenter`)
     - `ProductLineId` (`vpx`)
     - `FullName` and `InstanceUuid`
   - **Endpoint Validation (`ApiType`):** SIMS is designed exclusively for vCenter Server. Direct ESXi host endpoints (which report `ApiType: "HostAgent"`) are rejected with typed error `invalid_api_type` (`ErrInvalidApiType`).
   - **Version Parsing & Malformed Handling:** Version strings are parsed via semver pattern. Unparseable, non-numeric, or empty version strings are safely rejected with typed error `unparseable_version` (`ErrUnparseableVersion`) without panicking.
   - The session layer extracts `major.minor` (strictly bounded cardinality) for the Prometheus metric `sims_vcenter_info{vcenter_id, major_minor}`. High-cardinality fields (`api_version`, `build`, `full_name`) are captured in structured logs and persisted in `collector_state`.
   - Version details are stored on the `vcenters` table and exposed over the management API (`POST /v1/vcenters`, `POST /v1/vcenters/test-connection`, `GET /v1/vcenters`).

3. **Capability Flags Over Version Branching:**
   - Behavioral differences between vSphere versions (and between simulator vs real appliance) must be driven by capability flags detected or negotiated dynamically, never by scattered version branches:
     - **Tagging REST Endpoint Style:** In govmomi v0.56.0, `vapi/tags.Manager` issues requests using `/rest/com/vmware/cis/tagging/*`. While `/rest` was deprecated in vSphere 7.0U2 in favor of `/api`, it is retained for multi-version backward compatibility. The tag fetcher must be capability-driven with fallback, and must degrade gracefully via `ErrTaggingUnavailable` on failure without failing the core inventory pipeline (ADR-016).
     - **PropertyCollector Fault Handling:** Incremental change tracking uses `WaitForUpdatesEx`. The collector resilience layer handles both explicit `InvalidCollectorVersion` SOAP faults and transport timeouts (to handle vcsim's non-standard wait-loop behavior on stale tokens).
     - **Custom Attributes & Events:** Support both SOAP `CustomFieldsManager` (field definitions and VM `customValue`) and modern event structures across all supported versions.
   - A failed or missing capability degrades only that specific feature, never terminating the collector process or failing the entire vCenter connection.

4. **Client Library Negotiation:**
   - Govmomi `vim25.NewClient` initializes with `Version = "9.1.0.0"` and sends fixed `SOAPAction: urn:vim25/9.1.0.0`. Upstream vCenter SOAP services handle forward and backward API negotiation natively.
   - **Simulator vs Real Appliance Limitation:** `vcsim` accepts any `SOAPAction` header string without validation. Tests against `vcsim` configured as 7.0.0 confirm that SIMS's session layer parses and accepts a 7.0 `AboutInfo` and completes sessions, but do NOT prove that an actual vCenter 7.0 appliance accepts `"urn:vim25/9.1.0.0"`. Real vCenter 7.0 verification remains BLOCKED (human) until access to an appliance is provided.

5. **Test Matrix & Multi-Version Fleets:**
   - **`vcsim`:** Executed on every pull request. Tests version parsing with mock `ServiceContent.About` fixtures for 7.0, an older supported version, and newer versions (all accepted), pre-7.0 (rejected with `unsupported_version`), unparseable versions (rejected with `unparseable_version`), and direct ESXi endpoints (rejected with `invalid_api_type`).
   - **Real vCenter Targets:** Tested against available supported versions in lab environments, recording empirical findings per version column in `docs/vsphere-capability-matrix.md`.
   - **Mixed Fleet:** Sprint 4 scale testing and cross-vCenter migration (xvMotion) validate concurrent operation across a fleet containing differing supported vCenter versions (e.g. an older and a newer supported vCenter).

## Consequences
### Positive
- Full compatibility with modern vSphere deployments without code changes or ceiling blocks.
- Deterministic behavior: obsolete pre-7.0 endpoints fail fast with clear typed errors (`unsupported_version`).
- Clean architectural decoupling: capability flags isolate version quirks from core hydration and streaming logic.
- Clear operational policy: no artificial "untested" states; validation is tracked empirically in the capability matrix.

### Negative / Trade-offs
- Behavioral certification requires maintaining and validating real vCenter testbeds across available versions.
- Managing fallback pathways between legacy `/rest` and newer `/api` REST endpoints increases test surface area.
