# ADR-003: Type-Safe SQL with sqlc and pgx/v5

## Status
Proposed

## Context
Having decided against an ORM (ADR-002), the application requires a robust, type-safe mechanism to execute SQL queries in Go without writing repetitive boilerplate scanning code (`rows.Scan(&col1, &col2, ...)`), which is notoriously error-prone and brittle during schema migrations.

Furthermore, database schema evolution requires a migration tool that integrates seamlessly with compile-time code generation and supports both CLI and programmatic test execution.

## Decision
1. **Query Tool:** Adopt `sqlc` with `sql_package: pgx/v5`.
   - SQL queries are written in `db/queries/*.sql` with explicit names and return types (`:one`, `:many`, `:exec`).
   - `sqlc generate` verifies queries against the migration schema in `db/migrations` and produces compile-time type-safe Go structs and methods in `generated/db`.
   - Generated files are committed to version control and verified in CI via `make sqlc-verify`.
2. **Driver:** Adopt `jackc/pgx/v5` as the primary PostgreSQL driver and connection pool (`pgxpool`).
   - Utilizes the native PostgreSQL binary protocol for high performance and reduced serialization overhead.
3. **Migration Tool:** Adopt `goose` (v3.28.0).
   - Uses single-file forward and rollback annotations (`-- +goose Up` / `-- +goose Down`) within `db/migrations/`.
   - `sqlc` natively understands `goose` migration syntax.
   - `goose` can be run both via standalone CLI and programmatically in Go integration tests via `pgx/v5/stdlib`.

## Consequences
### Positive
- Strict compile-time type safety: schema changes that invalidate existing queries break compilation immediately rather than failing in production.
- High performance: `pgx/v5` binary wire protocol avoids string parsing overhead.
- No handwritten row scanning boilerplate.
- Deterministic, reproducible generated code.

### Negative / Trade-offs
- Dynamic query composition (e.g. arbitrary combinations of 20 optional filters) is challenging in static SQL with `sqlc`; dynamic search requires a dedicated query builder or search compiler pattern in Sprint 3.
- Developers must run `make sqlc-generate` after altering SQL files.

## Alternatives Considered
- **sqlx:** Provides struct scanning but lacks compile-time validation and code generation.
- **golang-migrate:** Robust migration tool, but requires splitting every migration into two separate files (`.up.sql` and `.down.sql`), which adds file clutter compared to `goose`'s unified format.
