# ADR-001: PostgreSQL as Operational Search Store

## Status
Proposed

## Context
The Distributed vSphere Inventory & Search Platform must index and query inventories spanning multiple vCenters, encompassing tens of thousands of virtual machines, hosts, clusters, datastores, and network portgroups. Users expect rapid full-text search, exact identifier lookup, folder hierarchy traversal, and compound filtering.

Common enterprise architectures introduce a specialized search engine (such as Elasticsearch or OpenSearch) paired with a relational primary database. However, this introduces dual-write consistency problems, replication lag, re-indexing operational overhead, and distributed split-brain failure modes.

## Decision
Use PostgreSQL 18+ as both the operational primary datastore and the search engine for v1.
- Utilize PostgreSQL extensions `pg_trgm` for trigram-based fuzzy and substring search.
- Utilize `ltree` for hierarchical folder and inventory path operations.
- Utilize GiST and GIN indexing for high-speed multi-attribute filtering.
- Defer introducing Elasticsearch or OpenSearch unless scale benchmarks (>1,000,000 VMs with high write concurrency) demonstrate query latency degradation that database tuning cannot resolve.

## Consequences
### Positive
- Single operational datastore: simplifies backup, restore, high availability, point-in-time recovery, and security auditing.
- Strict ACID transaction guarantees across writes, updates, and indexing.
- Zero replication lag between inventory ingestion and search availability.
- Dramatically reduced infrastructure footprint and operational cost for small-to-medium deployments.

### Negative / Trade-offs
- Heavy write workloads (continuous real-time event updates) can compete with complex analytical search queries for shared buffer pool and I/O bandwidth.
- Requires careful index design (partial indexes, trigram GIN indexes, expression indexes) and memory tuning (`shared_buffers`, `work_mem`).

## Alternatives Considered
- **PostgreSQL + Elasticsearch / OpenSearch:** Dual-store architecture. Rejected for v1 due to synchronization complexity, consistency lag, and operational maintenance overhead.
- **Document Store (MongoDB):** Flexible schema but lacks robust relational integrity, `ltree` hierarchical indexing, and predictable SQL compilation.

## Open Questions
- What is the exact search latency SLA for complex multi-attribute compound filters under active inventory ingestion at 500,000 VM scale?
