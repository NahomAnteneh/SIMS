# ADR-009: Dedicated PropertyCollector Session Ownership

## Status
Proposed

## Context
VMware vSphere provides the `PropertyCollector` SOAP API for streaming inventory changes. A client creates a `PropertyFilter` on a specific container view, and subsequent calls to `WaitForUpdatesEx` return incremental diffs (added objects, modified properties, removed objects) paired with a version token string.

However, `PropertyCollector` sessions on vCenter are stateful and bound to the authenticated user session. If multiple threads or workers share or concurrently poll the same `PropertyFilter`, version token progression becomes non-deterministic, causing missing updates or `InvalidCollectorVersion` faults.

## Decision
Enforce strict single-owner affinity for PropertyCollector streaming:
- Exactly one collector worker thread holds the active `PropertyCollector` session and filter stream for a specific vCenter target at a time.
- The worker maintains the sequential progression of the version token string returned by `WaitForUpdatesEx`.
- If the session disconnects or the server throws an `InvalidCollectorVersion` fault (indicating server-side filter eviction), the worker destroys any dangling view/filter, resets its state, and triggers a full snapshot re-synchronization.

## Consequences
### Positive
- Guarantees sequential and deterministic processing of inventory property changes.
- Eliminates SOAP session race conditions and unexpected filter state corruption.
- Clear error recovery: any filter failure predictably triggers the idempotent snapshot path.

### Negative / Trade-offs
- Property collection throughput for a single vCenter cannot be horizontally partitioned across multiple concurrent collectors; throughput is bounded by the single worker's processing speed and vCenter's SOAP response latency.

## Alternatives Considered
- **Partitioned Filters by Entity Type:** Creating separate PropertyFilters for VMs, Hosts, and Datastores across separate sessions. While possible, it multiplies the number of active SOAP sessions on vCenter and risks cross-entity referential integrity races (e.g. receiving a VM update before the host it resides on is indexed).
