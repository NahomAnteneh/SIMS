# ADR-004: COPY and Staging Table Persistence for Bulk Ingestion

## Status
Proposed

## Context
When connecting to a new vCenter or recovering from an extended outage, the platform must ingest full inventory snapshots spanning 10,000 to 100,000+ virtual machines and related topology objects (hosts, datastores, networks).

Executing individual `INSERT ... ON CONFLICT DO UPDATE` statements row-by-row over network round-trips creates severe write amplification, lock contention, and high CPU utilization, taking hours to synchronize large inventories.

## Decision
Adopt a two-tier bulk ingestion model using `COPY FROM STDIN` and staging tables:
1. **Streaming Load to Staging:**
   - The collector streams raw inventory objects into temporary or unlogged staging tables (`staging_virtual_machines`, `staging_hosts`, etc.) via PostgreSQL's high-speed binary `COPY` protocol (`pgx.CopyFrom`).
2. **Set-Based Merge in Single Transaction:**
   - Once the copy finishes, execute a single set-oriented SQL statement (`INSERT INTO virtual_machines SELECT ... FROM staging_virtual_machines ON CONFLICT (...) DO UPDATE ...`).
   - Identify deleted or decommissioned objects via anti-joins (`WHERE id NOT IN (SELECT id FROM staging_virtual_machines)`).
   - Truncate or drop the staging table.

## Consequences
### Positive
- Ingestion speed increases by 10x to 50x compared to individual parameter parameterized inserts.
- Minimal index churn: indexes on production tables are updated in bulk rather than per row.
- Ingestion progress can be monitored via `pg_stat_progress_copy`.
- Atomic swap: downstream search readers never see partially ingested or torn inventory states.

### Negative / Trade-offs
- Requires temporary disk and memory space for the staging tables during full snapshot runs.
- Set-based merge statements require careful concurrency control to prevent deadlocks with real-time event updates.

## Alternatives Considered
- **Direct Multi-Row Inserts:** `INSERT INTO vms VALUES (...), (...), ...` in batches of 1,000. Faster than single inserts, but still significantly slower and more memory-intensive than `COPY`.
- **In-Memory Diffing in Collector:** Computing inventory diffs entirely inside collector memory before issuing updates. Fails at large scale (>100,000 VMs) due to collector OOM risks and concurrency skew.

## Amendment (Sprint 2): Field-Mask Staging for Incremental Updates (Superseded by Application-Layer VMFieldMask)
The original proposed amendment specified extending staging table `stage_vms` with `field_mask BIGINT NOT NULL` for set-based merge queries.

**Implemented Mechanism:**
During Sprint 2 implementation, the database column approach was superseded. The staging table does **not** carry a `field_mask` column. Instead, field ownership and incremental delta semantics are implemented at the application layer via `collector.VMFieldMask` in `internal/collector/applier.go` and applied directly in `internal/persistence/incremental.go` (`ApplyVMIncrementalUpdate`):
- Pointer fields (`*string`, `*int32`, `*int64`, `*time.Time`): `nil` indicates absence in the changeSet (do not update database column).
- Non-nil pointer: column is updated with dereferenced value.
- Child slice collections (`NetworkInterfaces`, `CustomAttributes`): `nil` indicates absence (collection untouched); non-nil empty slice (`make([]T, 0)`) indicates explicit clearing of child collections.
- `vm_tags` is strictly owned by the Tag Synchronizer (`TagPoller`) and is never touched by incremental property streaming.
