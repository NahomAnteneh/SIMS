# ADR-006: No Kafka or NATS Message Broker in v1

## Status
Proposed

## Context
Enterprise distributed event processing often utilizes an external distributed message log or pub/sub broker like Apache Kafka or NATS to decouple event producers from database consumers.

In the vSphere inventory architecture, collectors receive SOAP updates and events from vCenter. A common design proposal is for collectors to publish raw events onto a Kafka/NATS topic, with separate consumer worker fleets processing and persisting them to PostgreSQL.

However, running a production-grade Kafka cluster requires ZooKeeper/KRaft, partition management, replication factor tuning, schema registries, and consumer group offset management. NATS JetStream adds similar operational footprint.

## Decision
Do NOT introduce Kafka, NATS, or any dedicated message broker in v1.
- The collector fleet will write directly to PostgreSQL using transactionally safe staging, lease management, and event deduplication tables.
- PostgreSQL itself acts as the single source of truth and state log.
- Inter-process notifications (if needed) will utilize PostgreSQL native `LISTEN` / `NOTIFY` or table polling.

## Consequences
### Positive
- Substantially simpler operational architecture and lower infrastructure requirements.
- Guarantees transaction atomicity: inventory state updates and event records can be committed in the same database transaction.
- Eliminates "dual-failure" recovery scenarios where broker is up but database is down (or vice versa).

### Negative / Trade-offs
- The collector fleet is coupled to PostgreSQL availability; if the database is unreachable, collectors must buffer events locally in memory or fail back to snapshot synchronization upon reconnect.
- Scaling out event consumers beyond database connection limits requires connection pooling (e.g. PgBouncer).

## Alternatives Considered
- **Apache Kafka:** Overkill for the event volume of tens of vCenters (tens to hundreds of events per second under normal conditions).
- **NATS JetStream:** Lightweight and modern, but still adds an unnecessary operational dependency for v1.
