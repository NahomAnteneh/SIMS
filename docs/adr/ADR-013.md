# ADR-013: Keyset Pagination for Search and Inventory APIs

## Status
Proposed

## Context
When searching or listing tens of thousands of inventory items, results must be paginated to keep API latency low and memory consumption bounded.

Traditional offset-based pagination (`LIMIT 50 OFFSET 10000`) suffers from two major problems:
1. **Performance Degradation ($O(N)$):** The database engine must scan and discard all 10,000 preceding rows before returning the requested 50 rows.
2. **Result Drift:** In an actively mutating inventory system where VMs are continuously created, deleted, or powered on/off, offset pagination results in skipped or duplicated items as rows shift positions between page requests.

## Decision
Adopt **keyset (cursor-based) pagination** across all search and listing endpoints:
- Every query sorts on a deterministic, unique composite key: `(sort_field, id)`.
- The API client passes an opaque base64-encoded cursor containing the values of `(sort_field, id)` of the last item from the previous page.
- Subsequent pages are fetched using index-seek predicates:
  ```sql
  WHERE (name, id) > ($last_name, $last_id)
  ORDER BY name ASC, id ASC
  LIMIT $page_size
  ```

## Consequences
### Positive
- Consistent $O(1)$ query performance regardless of how deep the user paginates into large result sets.
- Immune to insertion and deletion drift during traversal.
- Minimal memory footprint on both API servers and the database engine.

### Negative / Trade-offs
- Random access to arbitrary pages (e.g. "jump directly to page 47") is not supported; navigation is forward and backward via cursors.
- All sort columns must have a composite B-tree index paired with `id`.

## Alternatives Considered
- **Offset/Limit Pagination:** Standard but fundamentally unscalable for large inventories and actively streaming data.
- **Client-Side Virtual Scrolling with Full Fetch:** Pulling all 50,000 IDs to the browser. Overwhelms client memory and network bandwidth.
