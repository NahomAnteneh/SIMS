# ADR-016: vSphere Tags and Custom Attributes Ingestion Architecture

## Status
Proposed

## Context
Virtual machine search and detail inspection require rich classification metadata:
1. **Custom Attributes (Key/Value):** Legacy metadata configured per vCenter. Custom attributes are exposed over SOAP via `CustomFieldsManager` (field definitions) and the VM `customValue` property (integer key to string value).
2. **vSphere Tags (Category/Tag):** Modern classification system. Tags are **NOT** available via the SOAP API or `PropertyCollector`. They reside exclusively in the vSphere Automation REST API (`/rest/com/vmware/cis/tagging` or `/api/vcenter/tagging`).

Furthermore, the vSphere Automation REST API does not support change notification streaming: there is no equivalent to `PropertyCollector.WaitForUpdatesEx` or an event-driven webhook mechanism for tagging changes.

## Decision
1. **Ingestion Protocol Separation:**
   - **Custom Attributes:** Hydrated via SOAP alongside VM properties (`customValue`), with integer keys resolved to attribute names at normalization time using definitions fetched from `CustomFieldsManager.field`.
   - **Tags:** Hydrated via a dedicated REST client (`vapi/rest` and `vapi/tags.Manager`) using bounded batch queries (`ListAttachedTagsOnObjects` with chunks up to 500 objects). Tag and category definitions are preloaded during session initialization.

2. **Reconciliation & Streaming Model (Sprint 2/4):**
   - Because tags cannot be streamed via `PropertyCollector`, Sprint 2 streaming updates will NOT receive real-time tag change notifications.
   - Tag updates will be handled via scheduled background polling and reconciliation runs (Sprint 2/4). Full inventory hydration performs baseline snapshot synchronization.

3. **Field Ownership and Replace-Set Semantics:**
   - The SIMS collector exclusively owns rows in `vm_tags` and `vm_custom_attributes`. External consumers have read-only access.
   - Persistence employs replace-set semantics within the same database transaction as the VM upsert merge: existing tag and attribute rows for VMs in the batch are deleted and replaced with the hydrated set via binary `COPY FROM STDIN` into temporary staging tables.

4. **Failure Isolation & Graceful Degradation:**
   - A failure, timeout, or absence of the tagging REST service (such as unconfigured `vcsim` or network partition to the REST port) must **NEVER** fail the core inventory hydration pipeline.
   - When REST tagging fails, the collector logs a warning, increments `sims_tag_fetch_failures_total`, and continues inventory persistence with tags degraded.

## Consequences
### Positive
- Inventory synchronization remains resilient even during vSphere REST endpoint degradation.
- Batch compaction and replace-set staging guarantee idempotent persistence.
- High performance bulk queries using PostgreSQL compound indexes (`category_name, tag_name, vm_id` and `name, value, vm_id`).

### Negative / Trade-offs
- Tag changes will exhibit polling latency relative to near-instantaneous PropertyCollector VM events in future streaming sprints.
- Separate session management overhead for SOAP (`vim25`) and REST (`vapi/rest`).
