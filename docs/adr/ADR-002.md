# ADR-002: No Object-Relational Mapper (ORM)

## Status
Proposed

## Context
Many backend projects adopt ORMs (such as GORM, Ent, or Hibernate) to map relational tables to language-native structs. While ORMs simplify basic CRUD operations, they frequently introduce severe drawbacks in high-throughput and data-intensive systems:
- Unpredictable N+1 query patterns and inefficient generated SQL.
- Lack of first-class support for advanced PostgreSQL features like `ltree`, `int4multirange`, and `COPY FROM STDIN`.
- Obscured execution plans and difficulties in query optimization.
- Complex reflection and runtime overhead.

## Decision
Do NOT introduce an ORM. SQL is the explicit database contract.
- All database interactions must be authored as explicit SQL queries and version-controlled SQL migrations.
- Code generation will translate verified SQL into type-safe Go code (see ADR-003).
- Bulk ingestion will utilize native PostgreSQL protocol streams (`COPY FROM STDIN`) rather than struct-by-struct ORM inserts.

## Consequences
### Positive
- Explicit control over generated SQL queries, joins, and execution plans.
- Full access to PostgreSQL-specific data types, extensions (`pg_trgm`, `ltree`), and bulk operations.
- Zero reflection overhead at runtime; deterministic memory allocation.
- DBAs and engineers can optimize SQL directly using `EXPLAIN (ANALYZE, BUFFERS)`.

### Negative / Trade-offs
- Engineers must write explicit SQL for queries rather than relying on abstract method chains.
- Relational mapping requires schema migrations to precede query development.

## Alternatives Considered
- **GORM:** Popular Go ORM, but prone to reflection overhead, uncontrolled query generation, and inadequate support for PostgreSQL specialized extensions.
- **Ent:** Schema-as-code generator, but abstracts away raw SQL and makes advanced PostgreSQL features cumbersome.
